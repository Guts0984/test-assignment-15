# Тестовое задание: служба поддержки (helpdesk)

Сервис поддержки клиентов. Клиент пишет на email или через форму на сайте, обращение становится тикетом, система сама назначает его свободному агенту нужной команды и следит за сроками ответа (SLA). Агенты отвечают, переписка уходит клиенту письмом. Руководитель команды следит за нагрузкой и просрочками. Администратор настраивает команды, рабочие часы и правила.

Если что-то неоднозначно — решите сами и запишите решение в README. История коммитов — по этапам работы, CI на каждый коммит.

---

## Стек

| Часть | Что использовать |
| --- | --- |
| База | PostgreSQL 16 + Prisma (сырой SQL — где нужны блокировки, ограничения и полнотекстовый поиск). **Источник правды — Postgres** |
| Redis 7 | **BullMQ**: таймеры SLA, предупреждения и эскалации, назначение тикетов, входящие и исходящие письма, отложенная отправка, автозакрытие, опросы. **Адаптер Socket.IO** между копиями `api`. Потеря данных Redis ничего не теряет: ни писем, ни таймеров, ни назначений |
| `apps/api` | Node.js, NestJS: REST + OpenAPI (`@nestjs/swagger`), **Socket.IO** (`@nestjs/websockets`). В `docker compose` работают **две копии** за nginx |
| `apps/worker` | Отдельный процесс NestJS: обработчики BullMQ. Можно запустить несколько копий |
| `apps/web` | Next.js 15 (App Router), React 19. Клиент API **генерируется из OpenAPI**, TanStack Query, React Hook Form, Tailwind |
| `packages/shared` | Zod-схемы ввода, расчёт рабочего времени и сроков SLA — общие для `api`, `worker` и `web` |
| Тесты | Vitest; интеграционные — на настоящих Postgres и Redis; e2e — Playwright |

## Сценарии

### Клиент

1. Пишет письмо на адрес поддержки или заполняет форму на сайте (тема, текст, вложения до 10 МБ).
2. Получает письмо с номером обращения. Отвечает на любое письмо из переписки — ответ попадает в тот же тикет.
3. Открывает переписку по ссылке из письма без пароля и отвечает там же.
4. После закрытия тикета получает опрос «Оцените ответ» (1–5 и комментарий).

### Агент

1. Включает и выключает статус «на смене». Новые тикеты назначаются только агентам на смене.
2. Видит очередь своих тикетов, отсортированную по сроку SLA; видит, сколько времени осталось.
3. Открывает тикет: вся переписка, история, кто ещё сейчас смотрит или пишет ответ.
4. Отвечает клиенту или оставляет внутреннюю заметку, которую клиент не видит. Отправку можно отменить в течение 10 секунд.
5. Меняет статус, приоритет, команду; передаёт тикет коллеге.
6. Объединяет дубли: переписка переносится в основной тикет, дубль закрывается со ссылкой.
7. Ищет тикеты по тексту переписки, клиенту, номеру.

### Руководитель команды

1. Видит нагрузку агентов, очередь без назначения, тикеты под угрозой просрочки и просроченные — обновляется вживую.
2. Переназначает тикеты вручную.
3. Получает эскалации о просрочках.
4. Видит отчёт за период: время первого ответа (медиана и 90-й перцентиль), время решения, доля тикетов в SLA, оценки клиентов — по команде и по агентам. Период и фильтры — в URL.

### Администратор

1. Создаёт команды, задаёт рабочие часы, часовой пояс и праздники каждой команды.
2. Добавляет агентов в команды, задаёт лимит одновременных тикетов и языки агента.
3. Настраивает правила маршрутизации: по адресу, на который пришло письмо, по словам в теме, по языку.

## Правила

| Что | Правило |
| --- | --- |
| SLA | `urgent`: первый ответ 1 ч, решение 4 ч, круглосуточно. `high`: 4 ч / 1 рабочий день. `normal`: 8 ч / 3 рабочих дня. `low`: 2 рабочих дня / 5 рабочих дней |
| Рабочее время | считается по часам и праздникам команды, в её часовом поясе (например, `Europe/Kyiv` и `Europe/Warsaw`); переход на летнее время учитывается |
| Пауза SLA | в статусе «ждём клиента» срок решения стоит; ответ клиента снимает паузу |
| Смена приоритета или команды | срок пересчитывается от времени создания тикета по новым правилам |
| Предупреждение | на 80% срока — агенту; просрочка — руководителю и отметка в отчёте |
| Назначение | агенту команды на смене, с нужным языком, у которого меньше всего открытых тикетов; лимит одновременных тикетов не превышается; при равенстве — тот, кто дольше без нового тикета. Свободных нет — тикет ждёт в очереди команды и назначается, как только место освободится |
| Агент ушёл со смены | его тикеты без ответа клиенту за последний час возвращаются в очередь команды |
| Письма | новое письмо — новый тикет; ответ в переписке (заголовки `In-Reply-To`/`References` или номер в теме) — сообщение в существующем тикете; одно и то же письмо, доставленное дважды, учитывается один раз |
| Автоответы | письма-автоответы и отказы доставки не открывают тикет повторно и не порождают новый |
| Решён → закрыт | через 3 дня без ответа клиента; ответ клиента в решённый тикет открывает его снова; ответ в закрытый — новый тикет со ссылкой на старый |
| Опрос | один на тикет, ссылка действует 7 дней, оценку можно изменить в течение этих 7 дней |
| Объединение | только тикеты одного клиента; срок SLA — у основного тикета; объединённый тикет нельзя объединить ещё раз |

Статусы тикета: `new`, `open`, `waiting_customer`, `on_hold`, `resolved`, `closed`. Таблица переходов (кто и из какого статуса) — в README.

**История тикета:** создание, назначения и передачи, смены статуса, приоритета и команды, ответы, заметки, объединения, предупреждения и просрочки SLA — кто и когда.

**Сид:** 4 команды в двух часовых поясах, 80 агентов, 200 000 клиентов, 500 000 тикетов и 3 000 000 сообщений за 2 года. Около 2 000 открытых тикетов с идущими таймерами SLA, часть из них просрочится в течение 10 минут после запуска. Логины — в README.

## Почтовая заглушка

Отдельный сервис в `docker compose`:

- принимает исходящие письма по SMTP и показывает их на странице, с заголовками;
- умеет отправить в систему входящее письмо: кнопкой на странице и по HTTP — им пользуются тесты;
- в режиме хаоса (переключатель в `.env`):
  - входящее письмо доставляется дважды;
  - каждое десятое исходящее письмо получает временную ошибку SMTP;
  - иногда приходит автоответ или отказ доставки на отправленное письмо.

## Инварианты

Это главное, что проверяется. Каждый инвариант должен держаться при одновременных запросах, повторах, рестарте процессов и потере Redis, и на каждый нужен тест.

1. **Лимит агента не превышается.** 500 тикетов, пришедших одновременно в обе копии `api` и обработанных тремя копиями `worker`, — ни у одного агента не больше его лимита; нагрузка между агентами отличается не больше чем на один тикет; оставшиеся ждут в очереди и назначаются по мере освобождения.
2. **Тикет назначен одному агенту.** Автоматическое назначение, ручная передача руководителем и «Взять себе» агентом одновременно — в итоге один владелец и честная история.
3. **Сроки SLA точные:**
   - считаются по рабочим часам, праздникам и часовому поясу команды, включая ночь перехода на летнее время;
   - пауза «ждём клиента» не съедает срок;
   - предупреждение и просрочка срабатывают вовремя и ровно один раз, даже если воркер был выключен: после включения он догоняет пропущенное.
4. **Письмо учитывается один раз:** входящее, доставленное дважды или пришедшее одновременно в обе копии `api`, — одно сообщение; исходящее при временной ошибке SMTP повторяется и уходит клиенту ровно один раз.
5. **Отмена отправки работает:** отменённый в течение 10 секунд ответ не уходит клиенту никогда, даже если отмена пришла в момент отправки; неотменённый уходит один раз.
6. **Одновременные ответы:** два агента отвечают в один тикет одновременно — второй получает предупреждение «в тикете новое сообщение» и решает, отправлять ли; без подтверждения ответ не уходит.
7. **Объединение безопасно:** одновременные объединения A → B и B → A не создают цикл и не теряют сообщения; после объединения ответ клиента в старую переписку попадает в основной тикет.
8. **Фоновые задачи надёжны:**
   - `kill -9` воркера посреди обработки входящих писем — после рестарта все письма обработаны, дублей тикетов и сообщений нет;
   - несколько копий `worker` не выполняют одну задачу дважды;
   - задача, упавшая на ошибке, повторяется с паузой; исчерпала попытки — видна администратору.
9. **Потеря Redis ничего не ломает.** После `FLUSHALL` таймеры SLA, отложенная отправка, автозакрытие, назначение из очереди и опросы продолжаются и ничего не выполняется дважды.
10. **Живые обновления через обе копии `api`:**
    - новый тикет, назначение и смена статуса видны руководителю и агенту на другой копии меньше чем за секунду;
    - «кто смотрит и кто пишет» в тикете актуален: закрыл вкладку — пропал не позже чем через 30 секунд;
    - клиент переподключился — догоняет пропущенное и не показывает устаревшее;
    - события тикета получают только те, кому он доступен.
11. **Права — на сервере, в каждом эндпоинте и в сокетах:**
    - клиент видит только свои тикеты и никогда не видит внутренние заметки;
    - ссылка из письма открывает только свой тикет и перестаёт работать после объединения или по истечении срока;
    - агент видит тикеты своих команд;
    - руководитель — свою команду; администратор — всё.
12. **На некорректный ввод — понятная ошибка с кодом**, одинаковая по формату во всех эндпоинтах и описанная в OpenAPI; никогда «Internal server error».

Время в задачах (сроки SLA, 80%, 10 секунд, 3 дня, 7 дней) подменяется в тестах.

## Что сдать

- Репозиторий: `apps/api`, `apps/worker`, `apps/web`, `packages/shared`.
- Запуск: `cp .env.example .env && docker compose up --build`.
  - `docker compose`: `postgres`, `redis`, `api` ×2, `nginx`, `worker`, `web`, почтовая заглушка.
  - Миграции и сид создаются сами, других ручных шагов нет.
- Swagger на `/docs`; сгенерированный клиент совпадает со схемой — проверка в CI.
- Очередь агента и панель руководителя обновляются вживую; оставшееся время SLA считается по часам сервера.
- Редактор ответа: черновик не теряется при перезагрузке страницы; ответ и заметка визуально различаются.
- Формы с ошибками у полей; работа с очередью и ответ — с клавиатуры.
- Поиск по тексту переписки на сиде — быстрее 300 мс; очередь агента — быстрее 200 мс; отчёт за 90 дней — быстрее 1 с.
- e2e:
  - входящее письмо → тикет назначен агенту → агент видит его без перезагрузки → ответ → клиент получил письмо → клиент ответил письмом → сообщение в том же тикете;
  - два агента в одном тикете: оба видят друг друга, второй ответ требует подтверждения;
  - отмена отправки за 10 секунд — письмо не ушло;
  - тикет решён → перевод часов на 3 дня → закрыт → опрос → оценка видна в отчёте.
- README:
  - запуск и тесты;
  - как считаются сроки SLA: рабочие часы, праздники, часовые пояса, паузы, с примером;
  - как устроено назначение и почему лимит не превышается;
  - как письма связываются с тикетами и как исключены дубли;
  - список фоновых задач: когда ставятся, повторы, защита от дублей, восстановление после потери Redis;
  - как события доходят до клиента через две копии `api`;
  - таблица статусов тикета;
  - индексы и ограничения в базе;
  - принятые решения.
