- **A-07 Who may do what** (pure predicates in `packages/shared/src/permissions`):
  - _Admin_: everything, every team.
  - _Team lead_ (membership role `lead`): everything an agent can do on their teams' tickets, plus transfer to any agent of the team, manual close of `resolved`, dashboard and reports of their teams.
  - _Agent_ (membership role `agent`): view, reply, note, change status/priority/team, merge, transfer to a colleague of the same team, "take it" on unassigned tickets — only on tickets whose `team_id` is one of their teams.

- **A-08 Roles.** `users.role` is `admin` or `staff`; team membership role is `agent` or `lead`. An agent may belong to several teams. Leads are not auto-assignment candidates.

### 3.3 Authentication

- **A-09 Staff auth.** Email + password (argon2id; memory and time cost from env). Login → access JWT (HS256 pinned, `iss`/`aud`, 15 min, `sub`, `ver` = `users.token_version`) returned in the body and sent as `Authorization: Bearer`. Refresh token: 32 random bytes, stored SHA-256-hashed, 7 days, in an `httpOnly; Secure (when https); SameSite=Strict; Path=/api/v1/auth` cookie, rotated on every refresh. Reusing a rotated refresh token revokes the whole family. Logout revokes the family. Every request loads the user and memberships from Postgres, so deactivation and membership changes take effect immediately. The web keeps the access token in memory only and calls `/auth/refresh` on load. Login failures are identical for unknown email and wrong password (argon2 verify runs against a dummy hash for unknown emails).
- **A-10 Customer magic link.** 32 random bytes (base64url), stored as SHA-256 hash in `ticket_access_tokens` with `ticket_id`, `expires_at`, `revoked_at`. Scope: exactly one ticket. Every customer-facing email carries a fresh link valid 30 days (`MAGIC_LINK_TTL_DAYS`). All links of a ticket are revoked when it is merged into another; connected customer sockets of that ticket are disconnected. The link is put in the URL **fragment** (`/portal#token=…`), so it never reaches nginx or api access logs; the web sends it in the `X-Ticket-Token` header. Errors: unknown or tampered → `401 LINK_INVALID`; expired → `410 LINK_EXPIRED`; revoked by merge → `410 LINK_REVOKED`. Lookups compare hashes through a unique index (constant-time with respect to the secret).
- **A-11 Web form never grants access.** `POST /public/tickets` returns only the ticket number. The link goes to the email address, so submitting the form with someone else's address gives the attacker nothing.

### 3.4 Time

- **A-12 Controllable clock.** All code takes `now()` from an injected clock. Production clock = system time. When `TEST_CLOCK_ENABLED=true` (only in the `docker-compose.test.yml` override and in test runs, never in the default profile), the clock is `system time + offset`, where the offset is a single row in Postgres table `app_clock(offset_ms, generation)`. `POST /api/v1/test/clock` (registered only when the flag is on, guarded by the `TEST_CONTROL_TOKEN` header) sets or advances the offset and issues `NOTIFY app_clock`. Both api copies and every worker `LISTEN` and apply the offset immediately (1 s polling fallback). Workers run an immediate reconcile on every clock change. BullMQ job ids include the clock generation, so jobs delayed under the old offset are re-added and the stale copies become no-ops. With the flag off, the table is never read. SQL never calls `now()` for business decisions; `$now` is always a parameter from the injected clock.
- **A-13 Server clock in the UI.** Every API response carries `X-Server-Time`, and the socket sends `time:sync` on connect and every 30 s. The web computes `skew = serverNow − Date.now()` and all countdowns use `Date.now() + skew` (pure function in `entities/ticket/model`).

### 3.5 SLA

- **A-14 Hours vs business hours.** `urgent` = wall-clock 24/7 (1 h / 4 h). `high`, `normal`, `low` targets are business time in the team calendar: `high` 4 business hours / 1 business day; `normal` 8 business hours / 3 business days; `low` 2 / 5 business days. ACC-3 confirms business hours for `high`.
- **A-15 Team calendar model.** A team has an IANA time zone, a set of working weekdays, one daily window (`work_start`, `work_end`, local wall time) and a list of holidays (local dates, whole day closed). **1 business day = the length of the team's daily window** (09:00–18:00 → 9 business hours). Window bounds are local wall times; luxon resolves them per date, so DST nights are handled. A local time inside a DST gap moves forward to the first valid instant.
- **A-16 SLA start and measurement.** The clock starts at `created_at`. Outside business hours, business time starts at the next opening. First response = `created_at` of the first public agent reply that was not cancelled. If that reply is undone, the first response is cleared and its timers re-armed; overdue timers fire immediately. Resolution = first transition to `resolved`. A reopen re-arms the resolution timer from the original creation time.
- **A-17 Pause.** Only the resolution target pauses, only in `waiting_customer`. Pause intervals are stored (`sla_pauses`). Resolution deadline = `addBusiness(created_at, target + Σ businessTime(pause intervals))`. While paused, `resolution_due_at` is null and the resolution timers are suspended. ACC-5's "2 hours" are 2 business hours inside the window. For `urgent`, they are 2 wall hours.
- **A-18 Recalculation.** On priority or team change, all deadlines are recomputed from `created_at` with the new rules and the new team's calendar, including stored pauses. Already fired warnings or breaches stay fired and are never re-fired (one warning and one breach per ticket and target, enforced by a unique key). Unfired timers move. A new due time ≤ now fires immediately.
- **A-19 Warning and breach targets.** The 80% warning goes to the assignee (to the team leads if unassigned) as an in-app notification plus a realtime event. The breach goes to every lead of the team, sets `first_response_breached` / `resolution_breached` (counted in reports) and writes history. Leads are not emailed (in-app only).

### 3.6 Assignment and shift

- **A-20 Assignment rule** (pure `selectAgent` in shared, executed under a per-team Postgres advisory lock): candidates = team members with role `agent`, `is_active`, `on_shift`, `open_count < ticket_limit`, speaking the ticket language. If **no member of the team at all** speaks the language, the language filter is dropped so tickets never starve. Order: fewest open tickets → oldest `last_assigned_at` (never assigned first) → user id. "Open tickets" = assigned tickets in `new`, `open`, `waiting_customer`, `on_hold`. Tickets are taken from the team queue in `next_due_at` order (most urgent first), then by creation.
- **A-21 Limit is enforced everywhere.** Auto-assignment, lead transfer and "take it" go through the same DB guard: `agent_load.open_count` is maintained by a trigger on `tickets` that increments only if `open_count < ticket_limit` and otherwise raises `AGENT_AT_LIMIT` (→ 409). Lowering a limit below the current load is allowed. The agent then receives no new tickets until below the limit.
- **A-22 Take it / transfer.** "Take it" works only on an unassigned ticket (else `409 TICKET_ALREADY_ASSIGNED`). Agents transfer to a colleague of the ticket's team. Leads transfer to any agent of the team, including from someone else. All three paths lock the ticket row, so the history is linear.
- **A-23 Team change** clears the assignee; the ticket enters the new team's queue and is auto-assigned there.
- **A-24 Leaving shift.** In the same transaction as the toggle, every ticket assigned to the agent in `new`/`open`/`waiting_customer`/`on_hold` whose **last public reply to the customer (by anyone)** is older than 60 minutes before the shift-off moment, or missing, is unassigned (history: `returned_to_queue`, reason `shift_off`). Tickets with a reply in the last 60 minutes stay with the agent. Then a team assignment job is queued. Deactivating an agent or removing them from a team unassigns their tickets in that team.

### 3.7 Mail

- **A-25 Mail stub location and inbound path.** `apps/mail-stub` (plain Node, functional; `smtp-server` sink on 1025, HTTP UI/API on 8025). Inbound mail reaches the api as a raw RFC 822 POST to `http://nginx/api/v1/inbound/mail` (load-balanced over both copies) with `X-Envelope-To` and an HMAC-SHA256 signature `X-Inbound-Signature: t=<unix>,v1=<hex>` over `t.body` (secret `INBOUND_WEBHOOK_SECRET`, ±300 s by real time). The api parses headers, stores the raw message in `inbound_messages` (dedupe insert) and queues a durable job; it answers `202`. Unsigned or badly signed → `401 INBOUND_SIGNATURE_INVALID`.
- **A-26 Mailboxes and dedupe.** Support addresses are rows in `mailboxes` (seed: `support@`, `billing@`, `tech@`, `pl@` at `MAIL_DOMAIN`). Raw deliveries are unique on `(mailbox_address, rfc_message_id)`. Thread messages are unique on `rfc_message_id`, so the same email sent to two support addresses still produces one message. A missing `Message-ID` is synthesized as `<sha256(raw)@synthesized.invalid>`, so a byte-identical redelivery still dedupes.
- **A-27 Threading.** (1) `In-Reply-To` then `References` (newest first) are looked up among known thread message ids, our outbound ids included. (2) Otherwise the subject tag `[#<number>]`. A match counts only if the sender address (normalized, case-insensitive) equals the ticket customer's email; otherwise it is ignored (anti-forgery). Merged tickets resolve to their main ticket. Then by status: active → append; `waiting_customer` → `open` + end pause; `resolved` → reopen; `closed` → new ticket with `follow_up_of`. No match → new ticket routed by rules.
- **A-28 Autoreply and bounce detection** (pure function in shared). Autoreply if any: `Auto-Submitted` present and not `no`; `Precedence: bulk|junk|list|auto_reply`; `X-Autoreply`; `X-Autorespond`; Outlook/Exchange style (`X-Auto-Response-Suppress` containing OOF, AutoReply or All, or an "Automatic reply:" subject together with that header). Bounce if any: DSN content type, null return path, or a mailer-daemon/postmaster sender. A bounce is matched to our email only by the Message-ID it refers to (the sender is a mail server, not the customer) and then marks that outbound email `bounced`; it never creates or reopens a ticket.
- **A-29 Attachments.** At most 10 MB total decoded size per message (web form, portal reply, inbound mail). Larger form or portal uploads answer `413 PAYLOAD_TOO_LARGE`. A larger *email* is never dropped: the ticket or reply is created without the files and its text says which attachments were not stored. Raw inbound mail up to 30 MB is accepted (base64 overhead); nginx answers an oversize body with the same JSON error shape. Stored as `bytea` in a separate `attachments` table (Postgres is the single store, shared by all copies). Filenames are sanitized (basename, control chars removed, max 255). Downloads are permission-checked and served with `Content-Disposition: attachment` and `nosniff`. Agent replies are text-only.
- **A-30 HTML mail** is converted to text at ingestion; the UI renders text only.
- **A-31 Outbound exactly once.** Outbox row state machine `scheduled → sending → sent | failed | cancelled` with a lease. Each outbox row has a fixed RFC `Message-ID`. A transient `4xx` returns the row to `scheduled` with backoff, and a permanent `5xx` marks it `failed` (visible to the agent and admin). The only theoretical duplicate is a crash between the SMTP `250` and the commit marking `sent`. It is documented, and no test scenario relies on it. kill -9 tests target ingestion as the assignment specifies.
- **A-32 Undo boundary.** A reply is created with `send_after = now + 10 s`. Cancel succeeds only if `state = 'scheduled' AND $now < send_after` (single-row `UPDATE … RETURNING`). The worker claims only if `state = 'scheduled' AND $now >= send_after`. The decision is one row and one clock, so at exactly 10.000 s the cancel gets `409 UNDO_WINDOW_EXPIRED`. Customers (portal, socket) see a reply only after release (`released_at` set at claim), so a cancelled reply is never visible to them. Once a send has been attempted (`attempts > 0`, for example after a temporary SMTP error while it waits for its retry) the reply can no longer be undone: the undo window belongs to the first send only.
- **A-33 Concurrent replies.** A reply carries `lastSeenSeq` (per-ticket message sequence) and, after the warning, `confirmedSeq`: the newest message seq the agent saw in that warning. Under the ticket row lock, if any public, non-cancelled message has `seq > max(lastSeenSeq, confirmedSeq)` the answer is `409 TICKET_HAS_NEW_MESSAGES` with those messages and nothing is stored. A seq beyond the newest message is `400 VALIDATION_FAILED`, so a huge `lastSeenSeq` cannot switch the guard off; a confirmation covers only what existed when the warning was shown, so a message that arrives after it needs a new confirmation. (An API client can still read the ticket and send the newest seq as `confirmedSeq` without a human looking; the guard protects people, not scripts.) The editor remembers the seq from the first keystroke. Internal notes do not trigger the conflict.
- **A-34 Ticket numbers** start at 100000 (`#100123`); outbound subject `[#100123] <subject>`.

### 3.8 Jobs, Redis loss, realtime

- **A-35 Durable job model.** Postgres table `jobs` is the source of truth: `kind`, `ref`, `dedupe_key` (unique), `run_at`, `status (pending|done|cancelled|dead)`, `attempts`, `max_attempts`, `last_error`. Kinds: `inbound_process`, `assign_team`, `sla_warning`, `sla_breach`, `outbound_send`, `auto_close`. Survey and acknowledgement emails are `outbound_send`. BullMQ is the timing and transport layer: one queue per kind, job id `j:<id>:<attempt>:<clockGen>`, delay = `run_at − now`. A processor claims with `SELECT … FOR UPDATE SKIP LOCKED WHERE status='pending' AND run_at <= $now`, performs the domain change and marks `done` **in the same transaction**. A second copy, a duplicate BullMQ job or a re-delivery after a crash finds nothing to claim. On error: rollback, then `attempts+1`, `run_at = now + min(base·2^attempts, max)` with jitter, and re-queue. At `max_attempts` the status becomes `dead`, shown in Admin → Failed jobs with a "Retry" button. (Retries are Postgres-driven so the attempt count survives `FLUSHALL`.)
- **A-36 Reconciler.** Every worker runs a loop (`RECONCILE_INTERVAL_MS`, default 250 ms; also at startup and on every clock change). It re-adds BullMQ copies for all pending `jobs` rows due within `RECONCILE_HORIZON_MS` (10 min), ordered by `run_at`. It also ensures an `assign_team` job for every team with queued tickets and free capacity, re-queues stuck `inbound_messages` and unsent outbound mail, and every 30 s rebuilds the SLA timer rows of open tickets that have none. There is no advisory lock: every step is idempotent (unique `dedupe_key`, deterministic BullMQ ids), so several workers may run it at once. It needs no Redis state, so `FLUSHALL`, a Redis restart or worker downtime are recovered within one interval. Dead jobs are never re-armed by the reconciler (only a user action or an administrator does). A breach job also fires its pending warning first, so catch-up keeps the order.
- **A-37 Languages:** `en`, `uk`, `pl`, `de` (ISO 639-1). Ticket language = web form field → `Content-Language` header → detection with `franc-min` restricted to those four (confidence threshold) → the team's default language.
- **A-38 Routing rules.** Ordered list, first match wins. A rule matches when all of its set conditions hold: recipient mailbox equals; subject contains any of the keywords (case-insensitive, word boundary); language equals. Action: team (+ optional priority). No match → the mailbox's default team. Default priority `normal`.
- **A-39 Realtime.** WebSocket-only transport, so no sticky sessions are needed behind nginx. Rooms: `user:<id>`, `team:<id>` (staff of the team), `ticket:<id>:staff`, `ticket:<id>:customer`, `admin`. Joining requires a permission check against Postgres at join time. Team changes, membership removal and merges force `socketsLeave` / `disconnectSockets` through the Redis adapter on every copy. Events are produced after commit: by the api through the adapter, and by the worker through `@socket.io/redis-emitter`. A pure `routeRealtimeEvent` builds room/payload pairs; customer payloads come from a separate serializer with no note or internal fields. Every event carries the ticket `version`; the client ignores versions ≤ its cached version (no stale state). On reconnect, the client re-subscribes with `lastSeq` per open ticket, receives missed visible messages, and invalidates its TanStack queries (refetch from REST).
- **A-40 Presence.** Redis hash per ticket, entry per socket `{userId, name, state: viewing|typing, expiresAt}`, heartbeat every 10 s, entry TTL 30 s, removed on disconnect. Socket.IO ping 10 s / timeout 10 s detects dead connections within ~20 s. A reaper drops entries past TTL (covers a crashed api copy). Typing expires 5 s after the last keystroke.
- **A-41 No login throttle** (D-08).
- **A-42 Error format.** `{ "error": { "code": "VALIDATION_FAILED", "message": "…", "details": [{ "path": ["subject"], "code": "too_small", "message": "…" }], "requestId": "…" } }`. Stable codes: `VALIDATION_FAILED`, `MALFORMED_JSON`, `UNSUPPORTED_MEDIA_TYPE`, `PAYLOAD_TOO_LARGE`, `UNAUTHORIZED`, `INVALID_CREDENTIALS`, `TOKEN_EXPIRED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`, `INVALID_STATUS_TRANSITION`, `AGENT_AT_LIMIT`, `TICKET_ALREADY_ASSIGNED`, `TICKET_HAS_NEW_MESSAGES`, `UNDO_WINDOW_EXPIRED`, `TICKETS_NOT_MERGEABLE`, `TICKET_ALREADY_MERGED`, `LINK_INVALID`, `LINK_EXPIRED`, `LINK_REVOKED`, `SURVEY_EXPIRED`, `INBOUND_SIGNATURE_INVALID`, `MAIL_UNPARSEABLE`, `EVENT_BUDGET_EXCEEDED`, `INTERNAL_ERROR`. Inputs use `.strict()` zod schemas (unknown keys rejected → mass assignment impossible). One `ErrorResponse` schema is declared on every operation.
- **A-43 Generated client.** `apps/api/openapi.json` is emitted from the Nest app (`pnpm openapi:emit`, no DB needed) and committed. `openapi-typescript` generates `apps/web/src/shared/api/generated/schema.d.ts`. Runtime: `openapi-fetch` + `openapi-react-query`. CI regenerates both and fails on `git diff`.

### 3.9 Search, reports, seed, performance

- **A-44 Search.** `#123456` or a bare number → ticket number. Input containing `@` → customer email (prefix + `pg_trgm`). Otherwise full-text search with the `simple` configuration (multilingual, no stemming) over `messages.search_vector` (generated column, GIN) and `tickets.subject_vector`, plus customer name by trigram. Scoped to the actor's teams, ordered by ticket `updated_at`, limit 50, cursor pagination. Staff search includes notes; customers have no search.

Share within SLA = tickets with no first-response and no resolution breach ÷ tickets whose targets are decided (responded/resolved or breached). Ratings = average and count of survey ratings plus a 1–5 distribution. Grouped by team and by agent (assignee at resolution). Breaches are counted. Filters: `from`, `to`, `team`, `agent`, `priority`, all URL search params.

Teams: Support Kyiv (`Europe/Kyiv`, en/uk), Billing Kyiv (`Europe/Kyiv`, en/uk), Support Warsaw (`Europe/Warsaw`, en/pl/de), Tech Warsaw (`Europe/Warsaw`, en/pl). Ukrainian and Polish public holidays for 2025–2027. 80 agents (20 per team), 4 leads (one per team), 1 admin.

### 3.10 Misc

- **A-50 Mail stub specifics.** Messages are kept in an in-memory ring buffer (`MAIL_STUB_MAX_MESSAGES`). Chaos starts from `MAIL_CHAOS` in `.env`; tests can also flip it at runtime with `PUT /api/chaos`. Chaos decisions use a seeded PRNG (`MAIL_CHAOS_SEED`): every 10th SMTP transaction gets `451 4.3.0`, each inbound is delivered twice concurrently, and ~10% of delivered outbound mail triggers an autoreply or bounce back into the system. The stub never deduplicates; tests count raw deliveries.
- **A-51 Survey.** Created in the transaction that closes a ticket from `resolved` (auto or manual), never for merged duplicates. Unique per ticket, token hashed, expires `closed_at + 7 days` (by the injected clock). Rating 1–5 and comment can be changed until expiry; then `410 SURVEY_EXPIRED`.
- **A-52 Portal on a closed ticket** is read-only with a "reply creates a new request" action that behaves like an email reply to a closed ticket (follow-up ticket; the new link arrives by email).
- **A-53 Merge semantics.** `POST /tickets/:id/merge {targetTicketId}` merges `:id` (duplicate) into the target (main). Both are locked in id order (`ORDER BY id FOR UPDATE`, no deadlock). Both must be non-closed, not merged, same customer, different. Messages move with fresh per-ticket `seq`, outbox rows re-point, the duplicate is closed with `merged_into_id`, unassigned, its timers cancelled and its links revoked. Any earlier duplicates pointing at the source are re-pointed (flattened, depth ≤ 1). DB trigger forbids a ticket that has `merged_into_id` from being the source or target of another merge and forbids self-merge (cycle prevention at the DB level).
- **A-54 Integration test isolation.** One test database migrated once in global setup; every test creates its own teams, agents, customers and BullMQ queue prefix, so files run in parallel. Destructive suites (`FLUSHALL`, `kill -9`, clock jumps) run in a separate serial Vitest project and against the compose stack.
- **A-55 nginx.** Port `HTTP_PORT` (8080). `/api/` and `/docs` → `upstream api { api-1; api-2; }` round-robin. `/socket.io/` → same upstream with WebSocket upgrade. Everything else → `web`. nginx sets `X-Forwarded-For` / `X-Request-Id`; the api trusts proxy headers only from the nginx network. Body limit 15 MB at nginx (raw MIME with base64 overhead); the api enforces the 10 MB decoded limit. The mail stub UI is published on its own port (8025).

- **A-56 Pinned versions (verified in B1).** TypeScript 5.9 (the registry's newest major, 7.x, is not supported by the Nest/SWC/ESLint toolchain), Prisma 6, zod 3.25, Vitest 3, ESLint 9, Next 15.5, Nest 11, Node 24. pnpm 12 needs `allowBuilds` in `pnpm-workspace.yaml` for postinstall scripts.

Added to the env table: `POSTGRES_HOST_PORT`, `REDIS_HOST_PORT`, `TEST_DATABASE_URL`, `TEST_REDIS_URL`, `WEB_INTERNAL_API_URL`.

- **A-60 FSD lint test** shells out to the ESLint CLI from the repo root because `eslint-plugin-boundaries` resolves element patterns against `process.cwd()`.

- **A-61 Agent load lives on `users`** (`open_count`, `ticket_limit`) instead of a separate `agent_load` table. A trigger on `tickets` increments with `UPDATE users SET open_count = open_count + 1 WHERE id = $1 AND open_count < ticket_limit` and raises `AGENT_AT_LIMIT` when no row matches; user rows are touched in id order so swaps cannot deadlock. All writers (auto-assign, lead transfer, take-it) hit the same guard.

The application flattens earlier duplicates first and locks both rows in id order, so the opposite-direction race never reaches a deadlock.

Migrations: `0000_init` (generated from the schema + `pg_trgm` + ticket-number sequence starting at 100000) and `0100_guards` (raw SQL: checks, triggers, generated tsvector columns, GIN/trigram and partial indexes, `app_clock` row with a NOTIFY trigger).

- **A-66 Seed lives in `apps/api/src/seed`** (it needs argon2 and the shared SLA calculator) and is run by `node dist/cli/migrate-and-seed.js` (migrate, then seed). Historic data is bulk SQL (deterministic ids via `md5(...)::uuid`, text pools generated by a seeded PRNG, GIN/trigram indexes dropped and rebuilt after the load); the live set is built in TypeScript with the real calculator and inserted last, so timers are relative to the moment the seed finishes. Historic tickets' breach flags and timestamps are synthetic (plausible, not calculator-derived). The whole seed runs in one transaction, so a failed run leaves no partial data.

- **A-69 Auth details (B5).** Access JWT: HS256 pinned, `iss=helpdesk`, `aud=helpdesk-api`, claims `sub`, `ver`, `role`, `iat`, `nbf`, `exp`, time-checked against the injected clock. The guard re-reads the user on every request, so deactivation, role changes and a bumped `token_version` act immediately; the `role` claim is never trusted for admin routes (the database role decides). Logout revokes the refresh family and bumps `token_version`, which also kills outstanding access tokens. Refresh: the used-at update is one conditional `UPDATE ... RETURNING`; presenting a used token revokes the whole family (parallel refresh with one token: at most one wins). Unknown email and wrong password both run an argon2 verification and return the same body.
- **A-70 Every route declares its access** (`@RequireAccess('public'|'staff'|'admin'|'customer')`, exported as `x-access` in OpenAPI); a route without it is treated as admin-only. The route-table adversarial test enumerates the OpenAPI document and asserts 401 without credentials, 403 for an agent on admin routes, and that no route lacks a declaration.
- **A-71 Shared test clock implementation.** `app_clock(offset_ms, generation)` row + `NOTIFY app_clock` trigger; each process keeps an in-memory offset updated by LISTEN with a 1 s polling fallback. `POST /api/v1/test/clock {offsetMs | advanceMs}` exists only when `TEST_CLOCK_ENABLED=true` and needs `X-Test-Control-Token`. Suites that move the clock are `*.serial.spec.ts` and run one file at a time in a second Vitest invocation.
- **A-72 OpenAPI in the repo.** `apps/api/openapi.json` (default profile, so no `/test/*`) is committed and `scripts/openapi-diff.sh` regenerates it and the `openapi-typescript` client in `apps/web/src/shared/api/generated`, failing on any difference from the committed (CI) or staged (local) files. Swagger UI is at `/docs`, the JSON at `/docs/openapi.json`.
- **A-73 Error mapping.** Body-parser failures map to `MALFORMED_JSON` (400) and `PAYLOAD_TOO_LARGE` (413); non-JSON bodies on JSON routes are `UNSUPPORTED_MEDIA_TYPE` (415) via a content-type check (multipart/raw only under `/public/`, `/portal/`, `/inbound/`); unknown routes are `NOT_FOUND`; anything unexpected is a generic `INTERNAL_ERROR` with the stack only in the server log.
- **A-74 Agents who leave a team or are deactivated** have their tickets returned to the team queue (history event `returned_to_queue` with the reason) and an assignment run is requested; lowering a limit below the current load is allowed.

- **A-75 Ticket domain lives in `packages/core/src/tickets`** (transactional use-cases shared by api and worker): create, customer-message append/reopen/follow-up, ingest, reply/note/undo, status/priority/team/transfer/take, merge, close+survey, web form. Each takes a `Ctx {tx, now, cfg}` and returns `Result`; trigger-raised errors are mapped at the edge. The api's `TicketService` only adds permission loading and error mapping.
- **A-76 Merge chains.** A main ticket may collect several duplicates and later be merged itself; the migration `0200` dropped the "source is a main ticket" restriction. Cycles stay impossible (target must not be merged away; a merged ticket cannot be merged again). Replies resolve to the root through a recursive lookup. Customer links of the duplicate are revoked.
- **A-77 Cancelled replies** stay in `messages` with `cancelled_at` (audit); they are hidden from customers and excluded from conflict checks, first response and last-reply markers. Cancelling re-arms the first-response timers (`cancelled` jobs are re-armed; `done` ones never).
- **A-78 First response** is set when the reply is created (not sent). If it is undone and no other public reply exists, it is cleared. The customer sees an agent reply only after the sender releases it (`released_at`).
- **A-79 Anti-forgery** for threading: a Message-ID/References/subject-number match only counts if the sender equals the ticket customer's email (case-insensitive); otherwise the mail becomes a new ticket. Autoreplies/bounces from a non-customer sender (e.g. mailer-daemon) that thread to a ticket are dropped rather than attached.
- **A-80 Staff-visible 404.** Tickets outside the caller's teams answer 404 (indistinguishable from missing ones); role failures on routes answer 403. Report access is 403 for non-leads, 404 for another team's id.
- **A-81 Search** (`GET /search`): `#number` = ticket number; 4-12 digits are a ticket number first and, when no ticket has that number, a text search (a reference number written in a message); text with `@` = customer email substring (trigram); otherwise `websearch_to_tsquery('simple')` over messages (notes included for staff) and subjects, newest-updated first, plus customer-name matches (also when the text matches nothing). The tsquery is inlined as a constant and the message and subject conditions are resolved separately, never joined with OR. Per condition: (1) unless the planner knows the word is very common (it is in the column statistics, 100,000+ estimated rows), try to materialize every match from the GIN index under a 30 ms statement timeout: a rare word, a rare phrase or a narrow negation finishes at once and the result is complete; (2) otherwise walk the newest 5,000 tickets one by one (a phrase or negation: 2,500) through the `ticket_id` btree, with the tsvector concatenated with '' so the planner cannot pick the GIN index (it would read the word's whole posting list once per ticket), and stop when the page is full: the newest matches are exact; (3) a walk that does not fill the page means few or old matches: a single word is then materialized without a timeout, a phrase or negation gets one 150 ms attempt. Only a phrase or negation over very common words that still times out answers from the walk and covers the newest tickets only. The unknown-word estimate of Postgres is a flat 3,200 rows, so the estimate alone cannot tell a rare from a mid-frequency word; that is why the timed attempt exists. Measured on the full seed after a Postgres restart: single words 45-90 ms first call, phrases and negations 25-230 ms, results equal to a brute-force query for the first page.
- **A-82 TypeScript module settings.** `tsconfig.base.json` uses `module: ESNext` + `moduleResolution: Bundler` for typecheck and the editor; the `tsconfig.build.json` files of the CommonJS packages override to `commonjs`/`node10` for emit only (avoids the editor's node10 deprecation warning). The Prisma 6 `datasource url` is kept; `.vscode/settings.json` pins the Prisma extension to Prisma 6 so it does not apply Prisma 7 schema rules.

- **A-83 Mail stub behaviour (B7).** SMTP sink on `MAIL_STUB_SMTP_PORT` (no auth, no TLS), HTTP on `MAIL_STUB_HTTP_PORT`: `GET /` page (every message with all headers, HTML-escaped, plus the "Send inbound email" form), `GET/DELETE /api/messages`, `GET /api/stats`, `GET/PUT /api/chaos`, `POST /api/inbound` (JSON -> signed raw RFC 822 -> `MAIL_STUB_INBOUND_URL`). Chaos: every `MAIL_CHAOS_SMTP_FAIL_EVERY`-th SMTP transaction (counted over all attempts, including retries) is answered `451 4.3.0` and not stored; each inbound mail is posted twice concurrently with identical bytes; with probability `MAIL_CHAOS_AUTOREPLY_RATE` (seeded PRNG) an accepted outbound mail triggers an autoreply (`Auto-Submitted: auto-replied`, from the customer address) or a bounce (`MAILER-DAEMON`, `Return-Path: <>`, DSN content type), alternating, both with `In-Reply-To` of the sent mail.

- **A-84 Job execution (B8).** A BullMQ message is only a pointer `{jobId}`; the `jobs` row decides. `runTxJob` claims the row (`FOR UPDATE SKIP LOCKED`, pending and due) and the handler's domain writes plus the `done` mark commit in one transaction, so duplicate messages, three workers, or a crash cannot apply an effect twice. Failures roll back, then `attempts+1` and `run_at = now + min(base*2^attempts, max)` with 50-100% jitter are recorded in Postgres (so the attempt count survives `FLUSHALL`); at `JOB_MAX_ATTEMPTS` the row becomes `dead` (Admin: failed jobs, retry). Handlers: `inbound_process`, `assign_team` (200 tickets per transaction, `again` flag for the rest), `sla_warning`, `sla_breach` (a breach first emits a missed warning), `auto_close`, `outbound_send`.
- **A-85 Outbound send** is its own state machine (`scheduled -> sending (lease) -> sent | failed | scheduled again`). The claim is one conditional UPDATE using the same clock and `send_after` as undo, so cancel and send cannot both win. The lease (`OUTBOUND_LEASE_MS`, 60 s) is longer than the worst SMTP time (connect 5 s + greeting 5 s + socket 20 s), so a slow server cannot cause a second send. Transient SMTP errors go back to `scheduled` with backoff. Inherent edge: a worker killed between the SMTP `250` and the `sent` commit leaves a lease that expires, and the email is sent again with the same Message-ID, because SMTP gives the sender no way to learn whether a cut-off send arrived. The customer still receives it exactly once because the receiving side makes delivery idempotent on Message-ID, as real mailbox providers do; the mail stub does this (`MAIL_STUB_DEDUPE_MESSAGE_ID`, default true) and counts the repeats.
- **A-86 Reconciler** (every `RECONCILE_INTERVAL_MS`, default 1 s, in every worker): re-creates BullMQ copies of pending jobs due within `RECONCILE_HORIZON_MS` with deterministic ids `j<id>_<attempts>_<clockGeneration>` (adding twice is a no-op), detects an emptied Redis with a sentinel key (`SET NX`), drains and rebuilds after a test-clock change, and re-derives missing durable rows (queued tickets with a free agent, pending inbound mail, unsent outbound mail). BullMQ messages are removed on completion; stalled-job recovery is tightened (5 s) for `kill -9`.
- **A-87 Assignment** takes tickets of a team most urgent first under a per-team advisory lock and a row lock with `SKIP LOCKED`, picks with the shared `selectAgent`, and relies on the agent-load trigger as the final guard. Resolving/closing/transferring/removing requests a new run, so freed slots are filled within about a second.
- **A-88 Notifications.** SLA warnings create `notifications` rows for the assignee (team leads when unassigned); breaches create escalations for every active lead of the team. (Read API and realtime push arrive with the realtime block.)

- **A-89 Realtime mechanics (B9).** Every use-case records what it changed in a per-transaction collector (`created`, `updated`, `messages`, previous owners, access revocations). After the commit the api (and the worker) turn it into domain events by reading the committed state and publish them through `@socket.io/redis-emitter`; each api copy delivers to its own sockets through the Redis adapter, so a worker or either api copy reaches clients on both. A failed publish never undoes the work (clients refetch on reconnect). Events carry the ticket `version`; clients drop events not newer than what they hold.
- **A-90 Socket authentication and rooms.** WebSocket-only, handshake `auth: { token }` (staff JWT, same checks as HTTP, user re-read from the database) or `auth: { ticketToken }` (magic link). Staff join `user:<id>` and `team:<id>` for their teams (`admin` for admins); customers join only `ticket:<id>:customer`. `ticket:subscribe {ticketId, lastSeq}` re-reads permissions from the database, joins `ticket:<id>:staff`, answers with the ticket summary, the messages missed since `lastSeq` (notes included for staff) and the current viewers. Foreign ids get the same `NOT_FOUND` as missing ones. A team change drops everybody from the ticket's staff room (`ticket:access-changed`), a merge disconnects the duplicate's customer sockets, removal from a team / deactivation removes the user's sockets from the room / disconnects them.
- **A-91 Presence.** Redis hash per ticket (`hd:presence:<id>`, one entry per socket) with the injected clock's heartbeat time; entries older than `PRESENCE_TTL_SECONDS` (30) no longer count, are deleted by a reaper that runs in every api copy (about every TTL/6), and the room is notified (`presence:changed`). Closing a tab removes the entry immediately; an abrupt drop disappears by Socket.IO ping timeout (about 20 s) or the TTL. `typing` expires 5 s after the last keystroke event. Clients re-send `presence:update` every `PRESENCE_HEARTBEAT_SECONDS` (10).
- **A-92 Event budget.** `SOCKET_EVENT_BUDGET_PER_SECOND` (20) client events per second per connection; the excess is answered with `EVENT_BUDGET_EXCEEDED` and ignored. It is per socket, never per IP, and does not touch server-to-client delivery.
- **A-93 Notifications API.** `GET /notifications` (own SLA warnings / breach escalations) and `POST /notifications/read`.

- **A-94 Web architecture (B10).** Feature-Sliced Design under `apps/web/src` with the Next route files in `apps/web/app` as thin wrappers. `TicketList` lives in `entities/ticket` (several widgets use it, and widgets may not import each other). The access token is kept in memory only; the HttpOnly refresh cookie restores it on load and one shared refresh call serves concurrent 401s. All pages are client components rendered on demand (`dynamic = 'force-dynamic'`).
- **A-95 Live UI.** After login one WebSocket opens; every `ticket.created/updated/message.created` event whose version is newer than the last seen one invalidates the queue, team queue, dashboard, notification and open-ticket queries (refetch about 50 ms); a reconnect invalidates everything (catch-up). The ticket view re-subscribes after every reconnect and heartbeats presence every 10 s.
- **A-96 Server-clock countdown.** `X-Server-Time` on every API response (and `time:sync` on the socket) feeds one shared skew; every countdown is `dueAt - (Date.now() + skew)`, so a browser clock that is hours off still shows the server's time left.
- **A-97 Editor.** Drafts are stored per ticket and kind in `localStorage` (reply and note separately) and restored after a reload; the reply tab is a solid blue panel labelled "Public reply", the note tab a dashed amber panel with a lock and "visible to staff only"; a sent reply shows a 10-second undo bar (Undo button receives focus; the countdown follows the server clock); a 409 `TICKET_HAS_NEW_MESSAGES` shows the new messages with "Send anyway". Ctrl+Enter sends.
- **A-98 Keyboard.** Queue lists are one tab stop with Arrow/j/k/Home/End movement, Enter to open and `t` to take (team queue); controls are native elements with labels.
- **A-99 Report filters** (`from`, `to`, `team`, `agent`, `priority`) and the search text (`q`) are URL search params; changing them pushes a history entry, so reload and Back restore the exact view. `GET /api/v1/directory` supplies team and colleague names for pickers.
- **A-100 Customer pages** (`/portal#token=...`, `/survey#token=...`, `/new-request`) read the token from the URL fragment (never sent to a server log), keep it in `sessionStorage` for reloads, and use the `X-Ticket-Token` / `X-Survey-Token` headers.
- **A-101 Report cache.** `GET /reports` results are cached in memory for 15 s per filter set and per api copy (identical in-flight requests share one query). Reports are read-only aggregates, so a 15 s lag is acceptable; failures are never cached.

- **A-102 Reopen at the limit.** A customer reply to a resolved ticket whose agent is full does not fail: the message is stored, the ticket becomes `open` and returns to the team queue (`returned_to_queue`, reason `agent_at_limit`), and an assignment run is requested.
- **A-103 Queue order and skipping.** The assignment run takes tickets most urgent first, but a ticket nobody can take right now (for example its language has no free speaker) is skipped so it does not block the ones behind it; it waits for a speaker. The run stops at once when no agent at all is free. Each pick re-checks the agent's committed shift (`FOR SHARE`), so an agent who just went off shift gets nothing.
- **A-104 Dead jobs.** A job that used up its attempts stays `dead` (visible under `GET /admin/jobs/failed`) until a user action re-arms it; the reconciler never revives it.
- **A-105 Sessions and sockets.** An access token carries the id of its login session (the refresh-token family, claim `sid`); the guard and the socket handshake accept it only while that session is alive (no revoked token in the family). Logout revokes that session only: its access token stops working at once and its sockets (room `session:<id>`) are cut on both api copies, while other devices stay signed in. A token version bump (password change, admin action) still ends every session. A socket's handshake token is checked once; later subscriptions re-read the account, token version and session, so a socket keeps working after the 15-minute token expires, and the web client refreshes the session and reconnects after a refused handshake.
- **A-106 Web security headers.** Every page carries a CSP (`frame-ancestors 'none'`, `default-src 'self'`; scripts and styles allow `'unsafe-inline'` because Next inlines its bootstrap), `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: no-referrer`.
- **A-107 nginx** resolves the api copies through Docker DNS at request time (shared alias `api`), so a restarted copy is picked up within seconds. Containers run with `init: true`, so `docker stop` ends gracefully instead of SIGKILL.
- **A-108 Reports** cover at most 366 days; minute figures are rounded to one decimal. Percentiles are computed in the api from per-ticket minute arrays with the `percentile_cont` definition (linear interpolation), because the report needs several groupings from one pass.
- **A-109 Merge** asks for a second click ("Confirm: merge into #N") before it moves any message.

### 4.3 Data flow

```
 customer mail ──SMTP-ish──► mail-stub ──signed HTTP POST──┐
 browser (web, portal) ───────────────────────────────────►│
                                                    ┌──────▼───────┐
                                                    │    nginx     │  /api,/docs,/socket.io → api-1|api-2
                                                    └──┬────────┬──┘  /* → web
                                          ┌────────────▼─┐   ┌──▼───────────┐
                                          │    api-1     │   │    api-2     │
                                          └──┬───────┬───┘   └──┬───────┬───┘
                     tx: domain rows + jobs  │       │ BullMQ add │       │ Socket.IO redis adapter (pub/sub)
                                          ┌──▼───────┴───────────▼──┐  ┌─▼───────────────────────┐
                                          │  PostgreSQL (truth)     │  │ Redis (disposable)      │
                                          │  tickets, messages,     │  │ BullMQ queues, adapter, │
                                          │  jobs(due-at), outbox,  │  │ presence                │
                                          │  sla_pauses, history…   │  └─▲───────────────────────┘
                                          └──▲──────────────────────┘    │ BullMQ consume, redis-emitter
                                             │ claim FOR UPDATE SKIP LOCKED
                                          ┌──┴──────────────────────────┴──┐
                                          │ worker ×N (reconciler in each) │──SMTP──► mail-stub (sink, chaos)
                                          └────────────────────────────────┘
```

- **Postgres is the source of truth** for SLA timers, scheduled sends, the assignment queue, auto-close and surveys: every pending action is a `jobs` row with `run_at` (plus `outbound_emails`, `inbound_messages`, `tickets.assignee_id IS NULL` = queue). Every state change writes its domain rows, history event, follow-up `jobs` rows and outbox rows in **one transaction**.
- BullMQ jobs are copies. They are added after commit (best effort). If Redis is wiped or the worker is down, the **reconciler re-derives them from Postgres**. Processors are idempotent through the claim on the `jobs` row.
- Realtime: after commit, api emits through the adapter; worker emits through the redis-emitter. Both reach sockets on either api copy. Clients refetch on reconnect.

### 4.4 Key database guards (raw SQL in migrations)

- `agent_load` + trigger on `tickets` (assignee/status change): conditional increment `WHERE open_count < ticket_limit`, else `RAISE 'AGENT_AT_LIMIT'`; `CHECK (open_count >= 0)`.
- Single owner: `tickets.assignee_id` single column, all writers take `FOR UPDATE` on the ticket row; history in the same transaction.
- `UNIQUE (mailbox_address, rfc_message_id)` on `inbound_messages`; partial `UNIQUE (rfc_message_id)` on `messages`; `UNIQUE (inbound_message_id)` on `messages`.
- `UNIQUE (rfc_message_id)` on `outbound_emails`; state `CHECK`.
- Merge: `CHECK (merged_into_id <> id)`, `CHECK (merged_into_id IS NULL OR status = 'closed')`, trigger forbidding chains/cycles.
- `UNIQUE (ticket_id)` on `surveys`; `CHECK (rating BETWEEN 1 AND 5)`.
- `UNIQUE (dedupe_key)` on `jobs`: one warning and one breach per ticket and target, ever.
- `UNIQUE (ticket_id, seq)` on `messages`.
- Indexes: queue `(assignee_id, next_due_at) WHERE status IN (active)`; team queue `(team_id, next_due_at) WHERE assignee_id IS NULL AND status IN (active)`; reports `(team_id, created_at)` including the timing columns; GIN `messages.search_vector`, GIN `tickets.subject_vector`; GIN trigram on `customers.email`, `customers.name`; `jobs (run_at) WHERE status='pending'`; `ticket_events (ticket_id, id)`; `notifications (user_id, created_at DESC) WHERE read_at IS NULL`.

## 6. Threat model

**Assets:** ticket contents and attachments; internal notes; customer PII (email, name); magic links and survey links; staff accounts and tokens; agent load and assignment integrity; outbound mail reputation (no loops, no duplicates).

**Attackers:** (T1) another customer; (T2) a link holder after merge or expiry, or someone guessing/truncating tokens; (T3) an agent outside the ticket's team; (T4) a team lead of another team; (T5) an unauthenticated internet client; (T6) a forger of inbound mail (spoofed headers, unsigned webhook calls); (T7) a malicious socket client; (T8) an agent trying privilege escalation (mass assignment, admin routes).

## 7. Test plan

### 7.1 Unit (`SH:`, `MS:`, `WEB:`, plus `domain/` folders in api/worker)

- **Business time / SLA** (`SH:`): table-driven cases for each priority × target; ACC-3, ACC-4, ACC-5 exact instants; Kyiv and Warsaw spring-forward and fall-back nights; holiday on Monday, holiday on Friday, consecutive holidays, year boundary; creation inside/before/after window, exactly at open/close; zero duration; pause entirely inside, across closing, across a weekend, across DST; recompute on priority and on team change (different time zone). **Property tests (fast-check)** over random calendars, instants and durations: `businessBetween(t, add(t, d)) == d`; `add` is monotonic in `d`; `add(add(t,a),b) == add(t,a+b)`; the result is always inside a working window or at its end; with a 24/7 calendar `add == t + d`; pause shift equals the paused business time.
- **Status transitions**: full matrix of 6×6 pairs × actors (system/customer/agent/lead/admin), including all forbidden ones.
- **Assignment selection**: min load, tie by `last_assigned_at`, then id; language filter and its fallback; off-shift, inactive, leads excluded; limit; property: never selects an agent at limit; repeated selection keeps loads within 1.
- **Routing**: rule order, AND of conditions, keyword word boundaries, default team.
- **Mail**: subject tag parsing (`[#123]`, `Re: Fwd: [#123]`, look-alikes), Message-ID list parsing (folded headers, angle brackets, garbage), autoreply/bounce detection for each header rule and negatives (`Auto-Submitted: no`).
- **Permissions and realtime routing**: every role × resource; `routeRealtimeEvent` never sends notes or internal fields to customer rooms (property over random events).
- **Mail stub**: chaos PRNG determinism, every-10th counter, RFC 822 composition, signature.
- **Web model**: draft storage, server-clock countdown, API error → RHF field mapping, report filters ↔ URL, keyboard navigation reducer, realtime version guard.
